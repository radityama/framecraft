# Phase 3.5 Multi-Project and Multi-Scene Design

**Status:** Approved design, pending written-spec review. **Date:** 2026-10-22.

## Goal and limits

Make the existing manifest-driven HTML-shot pipeline work for independently selected projects and scenes. Keep `projects/demo` and its `intro` output working without migration. This is not an editor, database, new framework, hosted service, transition system, or new shot runtime. Rendering remains deterministic at requested frames; audio remains manifest-driven; replacement of rendered output remains atomic; visual capture never implies editorial approval. Leave unrelated untracked files, including `.taste-skill/`, untouched.

## One validated source of truth

`src/spike/project.ts` loads a canonical project root and validates `project.json`, all referenced scenes and shots, local HTML and audio paths, zero-overlap cuts, durations, audio trim bounds, IDs and uniqueness. A scene ID is unique within a project, a shot ID within a scene. Keep project-local relative asset URLs and the existing `window.framecraft.shot` API. Reject path traversal outside the project and symlink escapes using canonical paths, including discovery roots and referenced files. A project may have no scenes for Studio's empty state, but any selected render/review scene must exist and contain shots. Reject invalid or ambiguous selectors explicitly rather than quietly choosing another scene.

Expose one validated project-with-scenes representation to Studio and command callers, and a shared scene-selection operation. Preserve `loadProject(root)` for legacy single-scene callers where practical, but no export or review may derive its scene by reading the first JSON reference independently of validation. CLI `--project` accepts a directory path relative to the caller's working directory or absolute; omitted means `projects/demo` for render, snap, validate and review. CLI `--scene` accepts only a validated scene ID; omitted means the only scene when there is exactly one, otherwise requires an explicit scene. Studio's initial selection remains demo/intro for the no-argument invocation, with `--project` and `--scene` establishing its initial authorized selection. Keep validation of every scene in the selected project even when a scene selector narrows warning output or an export.

## Authorized Studio registry and URLs

At startup, `bun run studio` discovers direct child project directories under the repository `projects/` directory, canonicalizes their paths, and loads each independently. Invalid entries, including symlinks that resolve outside that directory, are skipped with a reported diagnostic rather than preventing other valid projects from opening. IDs must be unique in the authorized registry: an ambiguous duplicate cannot be selected. `bun run studio --project <path>` also authorizes that one explicitly named local project, even outside the repository, after full validation; it does not authorize its neighbors. The server binds to `127.0.0.1` by default. Browser-provided `project` and `scene` parameters are IDs, never paths; the server resolves them only against its startup registry and the selected project's validated scenes. Unknown, duplicate, malformed or unauthorized IDs fail closed. The existing `?clip=<scene-id>` demo deep link remains usable; new links carry validated `project` and `scene` IDs. Selecting a project or scene updates the URL, clears pending frame acknowledgements and mounts a fresh Player. Preserve loading, empty and error states, keyboard access, focus, touch targets and the current dark editing-workspace visual language. No browser endpoint accepts an arbitrary filesystem path.

The Studio server serves project-specific local assets only for authorized canonical project roots. It must keep realpath-based traversal and symlink checks on requests and isolate asset namespaces so equally named files from different projects do not collide. Bundling or previewing an authorized external project must not expose adjacent files. No remote assets or browser-supplied project roots are needed.

## Dynamic Remotion and command pipeline

Replace the hardcoded demo composition registration with compositions derived from the selected validated project and scene metadata. The selection is passed consistently to Remotion composition selection and rendering, including shot-local stills and scene-wide MP4, without changing the shared `SceneComposition`, `ShotView`, iframe bridge or runtime. Composition IDs must not collide for repeated shot IDs in distinct scenes; shot selections are scoped to the selected scene. The selected project's canonical root is the only `publicDir` for a CLI export. Preserve local asset loading, frame arithmetic, scene and shot audio placement and the atomic output-write behavior. Reject invalid project, scene, shot or frame before modifying an existing destination.

`bun run snap`, `bun run render`, `bun run review` (capture/check/summary), `bun run validate` and `bun run studio` recognize `--project` and `--scene` with the same path/ID semantics. A command that inspects a whole project (validation or Studio) still validates/discovers its scenes; selecting one scene does not silently excuse another invalid scene. Retain the validator's legacy positional project-root argument as an alias if existing tests or users rely on it, but reject conflicting positional and flagged roots. Scene-specific operations on multi-scene projects require `--scene`. CLI failures provide a concrete diagnostic and do not write a successful-looking output.

## Review integrity

Capture shots from the selected scene into a new immutable artifact directory. Record project and scene IDs, canonical-root source digest, validation result, git state, environment, exact selected frames and PNG hashes. `--check` and `--summary` verify the manifest's selected project and scene against the explicitly selected validated root, frame policy, decoded images and current digest; they do not default to another scene for a multi-scene project. Keep summary generation behind verification and never infer `accepted` or `needs-revision` from a successful capture. Reject review output and summary paths inside the selected project, including aliases through symlinks. Existing demo review artifacts remain readable under their current schema.

## Fixture, checks and documentation

Add a distinct repository project with at least two scenes and three total HTML shots, project-local fonts/images or other local assets, scene and shot audio that overlap, and scene/shot briefs usable by the portable agent workflow. Its shots expose visibly distinct first/middle/last frames for inspection. Keep all new assets local and licensed or authored in-repo; do not alter demo pixels or source assets merely to support the fixture.

Test loader and CLI selection, default demo compatibility, invalid project isolation, duplicate/unauthorized project IDs, malformed scene IDs, traversal and symlink escapes, cross-project asset access, same shot IDs in different scenes, output safety and review verification. Run `bun test`, `bun run typecheck`, validation of both projects, first/middle/last and reverse-seek still checks, a real browser Studio pass at desktop and phone widths across projects and scenes, and MP4 export plus ffprobe audio/video probing for the new fixture and the demo. Inspect retained visual artifacts and record an explicit quality decision instead of equating successful capture with acceptance. Update `AGENTS.md`, rendering/Studio/audio/agent-workflow docs and the portable Framecraft skills where they currently imply demo-only operation. Report command outcomes, browser observations, commit SHA/status and any remaining limitations.

## Compatibility and security boundaries

The framecraft authoring API, frame-seeded time/randomness, fonts/images readiness, Remotion Player clock, audio timeline and local-only operation remain unchanged. Existing demo shorthand commands and `?clip=intro` work. Discovery is repository-scoped; only a CLI argument can authorize an external root. Project content is trusted authoring input for local rendering, not a sandbox for executing hostile HTML; Studio's registry nevertheless prevents browser-origin filesystem selection and static-file traversal. Cross-machine pixel identity and arbitrary external media codecs remain outside this phase.
