# Preview Studio MVP Design

**Status:** Approved design, pending written-spec review. **Date:** 2026-10-22.

## Purpose and boundaries

Framecraft needs a local browser workspace for inspecting its validated HTML shots. The job is to select a scene, seek an exact global frame, identify its active shot, and play it without changing what the renderer produces. This is a preview, not an editor: no drag-and-drop, asset editing, audio, live video, transitions, database, MCP server, or separate rendering engine.

The existing demo project has one scene (`intro`) with four ordered shots of 60, 90, 60, and 120 frames at 1920×1080 and 30 fps (330 frames, hard cuts). A scene selector must support additional scenes declared in the unchanged `project.json` schema; a two-scene test fixture proves this without adding fictional scenes to the demo.

## Architecture

1. Extend `src/spike/project.ts` with a project-level validated scene-list result containing the existing video settings, project id/title, and each scene's id/title, `shots`, and `durationFrames`. Reuse one parser and the current path, symlink, duration, ID, zero-overlap, and empty-audio validation. A project with zero scene references yields Studio's empty state; an existing scene with zero shots remains invalid. Preserve `loadProject(root)`'s exactly-one-scene contract for current CLI callers; it must still reject zero or multiple scenes rather than silently rendering only one scene. A duplicate scene ID or invalid scene reference is an error. Never trust a scene path supplied by the browser: URLs select only IDs from the validated list.
2. Extract the existing Remotion `Sequence` + `ShotView` composition mapping into one shareable scene component. `src/spike/index.tsx` keeps registering the existing `intro` and four shot compositions from the same manifests, with unchanged frame counts and image behavior. Studio mounts the shared scene component in the installed `@remotion/player`, keyed by selected scene. `ShotView` and `projects/demo/runtime.js` retain their versioned same-origin iframe protocol, deterministic seeking, font/image settling, and latest-seek behavior. No second playback timer or animation scheduler.
3. A local-only Bun server (`bun run studio`) validates the demo project, bundles the Studio entry with the installed Remotion bundler and local project assets, serves the bundle and a validated read-only project manifest at `/api/project`, and removes its own bundle directory on shutdown. It binds to 127.0.0.1. The browser only requests local assets; there is no external API, hosted backend, or database. Project loading errors are shown in Studio or surfaced clearly by the server; invalid `?clip=` scene IDs show an actionable error and a valid scene choice, never a silent fallback. With no `?clip=`, select the first scene; selecting another scene updates history so reload preserves it.
4. Remotion Player is the sole play/pause and frame clock. Controls call its `play`, `pause`, and `seekTo`; its `frameupdate`, `play`, `pause`, `ended`, and `error` events drive UI state. Global frame is mapped to the validated shot by start/duration; the `<Sequence>` provides the shot-local frame. An origin- and source-checked iframe `rendered` acknowledgement marks a requested frame ready only when it belongs to the current scene/shot and latest requested global frame. While loading or seeking, obscure the old frame with a named loading state rather than show a stale preview. A seek failure or missing asset shows an error with retry, not a false-ready state. Switching scenes unmounts the old Player/iframe, removes listeners, resets frame/playing/loading state and clears old error; on end, pause at the last frame without looping.

## Interface direction

Reading this as: a production preview workstation for agents and video makers, dark and compact, **ENERGY 1 / RHYTHM 2 / MOTION 1**. Design-taste's app draw dealt `data-terminal` (seed 2088916148); choose it for aligned timecode and consistent selection marks in long editing sessions. Its generic graph-node canvas conflicts with the real product, so replace its palette with an ordered shot list and its graph with the actual 16:9 live preview. Keep its narrow accent line as the only selection hue; do not invent graph nodes, icons, drag grips, or fake data. Use the already bundled IBM Plex Sans for interface text and JetBrains Mono only for frame/time readouts: the shot type system ties the workspace to its output without a remote font dependency. Neutral dark surfaces, full-contrast text, and a small cyan-blue line for active shot/scene/timeline position distinguish state without decorative colour. Use text-only Framecraft identification, not an invented logo.

Header: product name, project title/id, native scene select. Main region: real 16:9 Player on a flat, dark stage, ordered shot list alongside it on desktop, stacked below the preview on a phone. Timeline: duration-proportional shot spans, current frame marker, accessible range input (0 through duration minus one), frame step buttons, play/pause, and current/total frame and time readouts derived from the scene fps. A clicked shot seeks its first frame and marks it active. Keep controls reachable with keyboard, visible focus, 44px touch targets and direct labels. At 1440, 768 and 390 widths, the preview stays usable without horizontal page overflow; the scene picker and transport remain visible. Mobile shows the preview before the shot list. No decorative entrance or repeating UI animation; playback itself is the motion.

All displayed data comes from the manifest. Initial loading says what is being loaded; an empty scene/project gives a concrete empty state; invalid route, missing shot asset, and runtime error give actionable error states with a valid scene selection/retry. A fixed dark theme is intentional for colour-accurate video inspection; no inactive theme toggle or dead control.

## Test seams and verification

Tests observe `loadProject` and the new validated scene-list API with temporary one- and two-scene projects; browser tests observe Studio at its local URL with real Remotion Player, scene dropdown, shot selection, frame range, play/pause, last-frame behavior, errors, and `?clip=` refresh. Prefer browser-visible state and iframe-rendered pixel output to private state or duplicated seek math. Compare arbitrary/reverse and rapid seeks, first/last shots, cleanup on scene change, and missing assets/runtime error. Use one small pure frame/time mapping test if it cannot be observed reliably in browser.

Run `bun test`, a type check and a Studio bundle build (adding TypeScript and Bun types as development-only dependencies only if needed for a real type check), `bun run validate`, and Studio in a real browser. Inspect console, click each control, and save representative screenshots at desktop/tablet/phone and frames from multiple shots. Run the existing full `bun run render` and ffprobe for exactly 330 frames at 1920×1080/30; compare the MP4's hash to a previously captured baseline only if matching output and environment are available, otherwise explicitly mark byte identity unverified. Preserve current rendering tests and document local startup, scene URLs, controls and limits in `docs/rendering.md` or `docs/studio.md`.

## Compatibility risks

- The current project loader rejects multiple scenes and the registered Remotion root hardcodes `intro`. Studio may read more scenes, but the current render command must keep its explicit single-scene guard until a deliberate export extension is designed; no migration or new demo scene is needed.
- `Player` can advance a frame before the iframe sends its settled-frame acknowledgement. Studio must distinguish a requested position from a ready image and never claim readiness from `frameupdate` alone. The real-browser tests decide whether existing `ShotView` behavior needs a focused repair.
- Local assets and WOFF2 fonts must resolve from the same origin as the iframe. Removing/rekeying a Player must release the old iframe and stop old events from affecting the new scene.
- Remotion's bundled headless browser and licensing remain as documented in ADR 0001. This phase does not establish cross-machine pixel identity or support audio/video/transitions.
