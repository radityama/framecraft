# Phase 3: Agent Visual Review Design

**Date:** 2026-10-22. **Status:** Design and written spec approved.

## Goal and current boundary

An agent using ordinary repository files and CLI commands can plan, author, capture, inspect, revise and deliver a Framecraft video. No embedded AI provider, mandatory MCP server, cloud inference, database, renderer replacement, heavy dependency, or narration generation is added. `AGENTS.md` remains the canonical entry point. Narration remains opt-in through supplied local media; the workflow never generates it.

The existing validated project/scene loader, HTML shot API, Studio, `snap`, `hash`, Remotion still renderer, audio timeline and atomic MP4 export remain authoritative. `snap` already writes a requested still, Studio seeks, and `hash` checks twelve fixed demo frames but deletes its stills. The missing capability is a review run that selects frames from the current scene, retains them with metadata and failure records, and requires a separate visual judgment. Do not change the fixed-frame `hash` report or existing CLI output defaults. The current renderer registers the one demo scene statically, so the new capture command initially targets `projects/demo` and its single exportable scene; the guidance must not claim other scenes/projects can already export.

## Review workflow and authoring guidance

From `AGENTS.md`, link six small local `SKILL.md` guides for storyboarding/shot planning, HTML shot authoring, motion timing, visual inspection/revision, sound placement, and final export/delivery. The guides reference the existing manifests, `docs/rendering.md`, `docs/audio.md`, Studio and CLI rather than copying their full API. A short compatibility note explains that any coding agent can read `AGENTS.md` and these Markdown files directly; installing a provider-specific skill or running an MCP server is optional, not a prerequisite. The guides must work through source files, commands and review artifacts, with no hidden tool state.

The human or agent reads the project and scene manifests, then the creative brief/shot requirements; authors or revises HTML shots; runs validation; captures selected frames; opens the actual PNGs; records visual defects and targeted fixes; recaptures in a **new** review directory after a change; repeats until the stated criteria pass; renders the full scene and checks its audio/video streams. For the demo, add a brief beside its scene manifest explicitly labelled **intent inferred from the existing four shot HTML files, not an original client brief**. It names title reveal, diagram pulse/result animation, readable close, and commit typing/output/rule as review criteria, plus explicit reveal milestones. Do not fabricate a broader creative brief. The final report must name observed issues and revisions, or explicitly state that no defect/revision was warranted.

## Deterministic frame selection

Use the validated shot order, shot duration and global `startFrame` from `loadProject()`. For each shot of `n` frames select local `0`, `floor((n - 1) / 2)`, and `n - 1`; when `n >= 90`, also select `floor((n - 1) / 4)` and `floor(3(n - 1) / 4)`. Combine optional explicit `--milestone <shot-id>:<local-frame>` values for animation/reveal events. Reject an unknown shot, noninteger/negative/out-of-range frame or malformed milestone before creating artifacts. Deduplicate local frames per shot and sort by global frame (then shot ID as a tie-breaker). `globalFrame = shot.startFrame + localFrame`; all selected frames are within `[0, scene.durationFrames)`. For `n = 1`, the first, middle and last collapse to one capture. The selection policy is versioned `boundaries-midpoints-v1`, and the manifest records all explicit milestones and selected local/global pairs. The demo's four shots yield 16 default stills before explicit milestones, not hundreds.

At zero overlap, each shot's last frame and the next shot's first frame are the two sides of every cut. A future transition implementation must version the policy and include the transition's incoming/outgoing boundary and its midpoint, using the then-authoritative transition timing; Phase 3 does not invent or implement transitions.

## Capture and artifacts

Add `bun run review --output <new-directory> [--milestone shot:frame ...]` (with a default under ignored `output/reviews/`). It uses `loadProject()`, the existing validation command for static warnings, one Remotion bundle, one browser, registered shot compositions, and `renderStill()` with the same local assets and frame semantics as `snap`/`hash`. It validates composition duration, width, height and fps against the loader before capture. The command rejects an existing output directory and rejects output inside `projects/demo/` so it never overwrites a prior review or modifies source. A caller can choose `docs/reviews/demo-intro/` to commit the demonstrated artifacts. Captures use deterministic basename `screenshots/<shot-id>-local-<zero-padded-frame>-global-<zero-padded-frame>.png`, with at least four digits of padding and wider digits when necessary. A capture writes to a temporary filename and is published only after nonempty PNG validation and SHA-256 hashing. Browser console errors and failed stills fail that frame; do not silently use an older PNG.

`manifest.json` has `schemaVersion: 1`, `projectId`, `sceneId`, `source` (`gitCommit`, tracked/untracked dirty indicator for project sources, SHA-256 digest of sorted project files), `selection` (policy and explicit milestones), `environment` (Bun, Remotion, Chromium, OS/platform/arch/release, video width/height/fps, font inventory if available), `validation` (command result and warning/error strings), `captures` (shot ID, local and global frame, relative PNG path, SHA-256 on success, status `captured` or `failed`, and error on failure), and `review` (`unreviewed`, `needs-revision`, or `accepted`; reviewer kind/name, findings, notes). A run never auto-sets `accepted`; reviewers edit the review section only after opening the PNGs. They distinguish visual findings from mechanical validation. A summary Markdown file renders the current manifest in a short table and includes review status/findings, not a generic quality claim. `bun run review --summary <manifest>` regenerates it after human/agent review. `bun run review --check <manifest>` is read-only: it validates the schema, shot/global frame references against the validated source scene, relative paths contained in the artifact directory, existence and hashes of every successful screenshot, failure entries, the source-project digest and summary freshness. It never promotes review status. The historical `gitCommit` need not equal current HEAD after review artifacts are committed; the project digest must still match. `accepted` requires a named human/agent reviewer and notes describing what was inspected; only a reviewer may assert subjective quality.

On a failed capture, the command records that frame as `failed` with an error, writes the manifest and summary for the run, cleans its partial PNG/bundle/browser, and exits nonzero. Remaining selected frames need not be captured once a fatal browser failure occurs; if present, they are recorded as failed/skipped with a clear reason so the manifest remains complete. A manifest with a missing PNG, invalid frame, mismatched hash, capture failure or stale summary fails `--check`. Invalid metadata or milestones fail preflight without creating an artifact directory. The project-file digest is compared before and after capture; a changed source invalidates the run rather than presenting mixed-revision evidence. A forced process kill may leave temporary files, as with existing commands.

## Demo review and verification

Capture the demo in a checked-in review directory using only a handful of explicit reveal milestones derived from the inferred brief. Open and inspect each resulting PNG, including all first/last and boundary pairs. Record specific visual findings, revisions and the final reviewer decision in the manifest and summary. If a shot requires correction, change only that shot/manifest as needed, preserve prior review artifacts, rerun capture and inspect again. Render the 330-frame 1920×1080/30 fps scene and independently inspect video and audio streams; existing audio mix tests remain authoritative for cue behavior. A final Phase 3 report references the review artifact paths, source revision, exact checks and results, visual issues/revisions (including an explicit none if applicable), and remaining limits. Never infer subjective approval from a passing test or unchanged PNG hash.

Pure unit tests cover frame selection for one-frame/short/long shots, cuts, deduplication, milestones and invalid references; artifact naming and manifest validation tests cover paths, hashes, missing/tampered images, stale summary and failed captures. A bounded integration test captures to a temporary directory, rechecks stable hashes on unchanged sources in another directory, exercises a deliberately failed capture through an injected still-render function (no production failure flag), and verifies project source bytes/status were not modified. Existing `bun test`, `bun run typecheck`, `bun run validate`, Studio browser tests, audio export tests and the final render must pass. No second-machine pixel identity or human listening test is implied.
